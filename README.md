# Casefile Provenance Demo

An interactive demonstration of how a changed assessment can trigger human review of a decision that depends on it. A fictional case connects the visible timeline to a Python ledger, preserving earlier evidence and decisions.

[Open demo](https://forest-savage1234.github.io/casefile-provenance-demo/) · [Three experiments](#three-experiments) · [Run locally](#run-locally) · [Verification](docs/verification.md)

**Work by Forest Savage:** the browser demonstration, adapter, fictional fixture, controls, and recorded outputs, integrating the existing [Decision Review Ledger](https://github.com/forest-savage1234/dfrws-lead-review). Source provenance and reused components are documented under [Source, attribution, and preservation](#source-attribution-and-preservation).

**Status:** Research demonstration using fictional records. It identifies decisions for review through declared dependencies; it does not rank police leads, establish an identification, or choose the next decision. See [Contribution and scope](docs/contribution-scope.md).

Compare a changed assessment, an editorial-only change, and a missing dependency. The interface labels recorded results and optional live Python execution separately, and lets you export the engine record for inspection.

## Try the real engine

In the fictional case, a witness report stays unchanged while a human revises the identification assessment after reviewing new footage. The ledger identifies the earlier decision that depends on that assessment. A simulated human reviewer records a successor decision; the tool does not make that choice.

1. Open the demo and select **Next** to reach **New footage changes the assessment** (stage 05).
2. Read **What the tool computes**. Initially, it shows **Recorded engine output**, generated by the Python engine.
3. Select **Run actual tool**. The browser loads Python, checks the copied source files against their manifest, and executes the same ledger. **Live Python engine** appears only after its result matches the recorded result.
4. Inspect the review request and its dependency path. The original decision is retained; the request asks a human to reconsider it.
5. Advance to stage 06. The simulated reviewer appends a successor decision and a review record.
6. Select **Export engine record** to inspect the complete ledger for the selected stage and experiment.

Live execution needs an internet connection for the pinned Pyodide 0.29.4 runtime and SQLite support. The browser runs the Python locally; it does not upload case data to a case-processing service. Loading can take a moment. If the runtime cannot load, the explicitly labeled recorded result remains available. Recorded output is not presented as a live run.

The **Export story provenance** button separately exports the illustrated case view as JSON-LD. The Python ledger export and the story's PROV-O illustration are distinct representations.

## Three experiments

The story timeline always shows the same fictional case. These controls change the engine experiment, not the story's outcome.

| Control | What is supplied to the engine | What to examine at stage 05 |
| --- | --- | --- |
| **Case story** | A changed identification assessment and its declared path to decision D1. | D1 receives a human reassessment request. |
| **Note-only control** | Source bytes change in an editorial note; mapped assessment fields stay the same. | A different source version alone does not create the same review request. |
| **Missing-link control** | The relevant assessment changes, but the decision's dependency coverage is undeclared. | Coverage is incomplete. The missing request cannot establish that no review is needed. |

This comparison is the core demonstration: **a byte change, a change in a decision's recorded basis, and a missing dependency are different conditions.** The two controls do not append D2, because they produce no machine request for the simulated review.

## What the case shows

| Stage | Case development | Relationship to the engine |
| --- | --- | --- |
| 01 | Intake. | Begin with the records available at that stage. |
| 02 | A witness reports a child beside a red van. | Record an identification assessment and the decision depending on it. |
| 03 | Two similar tips arrive. | Preserve separate records without assuming independent corroboration. |
| 04 | An analyst records their shared origin. | The common-origin finding is supplied by a human; the engine does not discover it. |
| 05 | New footage prompts a revised human identification assessment. | Compare mapped fields and follow declared dependencies to D1. Keep the witness report intact. |
| 06 | Separate observations support a new search direction. | A simulated reviewer appends D2 and its review record in **Case story**, preserving D1. |
| 07 | The fictional child is found safe. | Retain the outcome and the earlier record. The engine does not predict or establish recovery. |

Use **Back**, **Next**, or the **Investigation timeline** slider to inspect each stage. **Play / Pause** advances the story; **Reset** returns to intake. Select a source, report, or decision to inspect the illustrated relationships. Observation times and receipt times are recorded separately. Returning to an earlier stage reconstructs the knowledge recorded at that stage.

## Run locally

Use Node.js 22 or later for the local server and JavaScript checks:

```sh
npm test
npm start
```

Open [the local demo](http://127.0.0.1:4173). This is a static GitHub Pages application. The optional live engine uses a Python runtime downloaded by the browser; there is no application backend. The Python ledger is in memory and is recreated for each selected stage and experiment. Download the export to retain a run.

For native engine checks, also use Python 3.12 or later:

```sh
npm run test:python
npm run verify:engine
```

The verifier compares the copied source hashes and all 21 committed recordings with fresh engine runs. See [`actual_tool/README.md`](actual_tool/README.md) for the adapter contract. To regenerate recordings after an intentional adapter or fixture change, run `python scripts/verify_actual_tool.py`, inspect the resulting manifest and recordings, then rerun the checks.

See [Verification and boundaries](docs/verification.md) for the checks actually performed. For a lecture, test the deployed QR link on the venue network and keep a recorded walkthrough available.

## Limits and contributions

Every person, report, location, timestamp, and outcome is fictional. The footage is represented by a fictional review record; no video is analyzed. The tool compares explicitly mapped structured fields and declared links. Entirely new sources do not trigger reassessment of decisions without a recorded dependency path. Unrecorded relationships remain outside its view. Human actor labels are not authenticated identities. Internal digest and replay checks do not authenticate source truth or prove a forensic chain of custody.

This is a lecture demonstration, without validated police workflows, multi-user coordination, an enduring storage service, or operational lead prioritization. Keep contributions fictional, retain source attribution, document the provenance distinction demonstrated, and run the relevant checks. Do not add real case data or private meeting notes.
